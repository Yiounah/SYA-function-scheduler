# Scheduler 模块说明与功能创新

本说明面向 SYA 项目成员、演示评审和后续开发者，说明 Scheduler 的作用、操作方式、工程设计与专注评估边界。基线为 2026 年 10 月 28 日的本地源码，功能范围以本模块需求和《Schedule_闫羽_补充实现与API对接》为依据。本轮仅完善 Scheduler 及其在 SYA-UI 中的呈现。

Scheduler 把长期目标转换成有来源关系的四层任务树，再将尚未执行的工作放进可用作息。用户遇到任务过大或时间不足时，可以先看细化、合并和作息调整的影响，确认后保存。它提供计划与执行记录，不能独自判定用户的心理注意状态。

## 作用与功能范围

- **长期目标规划**：目标、阶段、子任务、清单四层结构；支持模型草案、手动编辑和明确标记的示例规划。模型错误不会伪装成成功。
- **多个项目共用日历**：项目保持独立，工作时段统一分配。日、周、月读取同一份服务器排期，不复制任务。任务量超过可用时间时顺延并提示截止风险。
- **任务粒度调整**：选择项目、阶段、任务或清单，按目标分钟数细化或合并未开始的工作段。保留总预计时长、来源和已执行节点。
- **作息调整**：配置工作起止、用餐时段、专注时长、短休息与周期性恢复；先查看前后安排及受影响任务，再确认应用。
- **执行与改期**：清单可更新状态和计划日期。开始专注交由主 APP 的 Focus owner，任务完成与计时状态分开维护。
- **安全确认与恢复**：预览不改正式计划；取消不采纳；确认校验版本与请求编号。保存的任务、进度、作息、排期及确认回执可在重启后读回。

独立窗口保留阶段浏览、搜索和时段外操作提示。SYA-UI 保持现有导航、浅色卡片与蓝色主操作，使用 FunctionHost 调用同一 Scheduler 服务。两处界面的布局可以不同，正式数据和调整规则一致。

独立窗口通过左侧“新建规划”开始规划，顶栏不再重复显示同名按钮。窄屏时保留同一个主按钮并显示在工作区上方。

## 任务树工作区（2026-10-28）

顶部保留课题名称、周期、完成期限、整体进度和“修改规划”。下方用一棵树展示四层关系：课题 → 横向阶段 → 纵向子任务 → 下属清单。阶段和子任务的标题是可折叠按钮，支持键盘 Enter/空格；每层展示完成数量，清单保留勾选完成操作。

阶段通过左右箭头排列，子任务和清单通过上下箭头排列。排序只发生在同一父节点下，首尾方向禁用；保存成功后更新正式树和未执行排期。已完成/执行中的状态、任务 ID、日期及历史执行时间块保留。这里不包含拖拽或跨阶段移动。

“全部展开/全部收起”控制当前课题。展开偏好通过既有配置接口写入 `focusflow.treeDisclosure`，按课题和节点 ID 保存，浏览器缓存仅用于快速显示。搜索临时打开匹配路径，清空搜索恢复原来的展开状态。窄屏仅在阶段区域横向滚动，长标题会换行。

日、周、月日历保留为辅助视图；点击任务可回到树中对应清单。SYA-UI 从“任务规划 → 高级规划器”打开相同界面，Electron 为两个入口提供同一份本地计划目录。该界面复用原有四层模型、配置和排序接口，没有增加任务树组件库。

交互参考 [WAI-ARIA Disclosure Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)，使用原生按钮的 `aria-expanded` / `aria-controls` 表达折叠状态，不冒充需要另一套键盘导航的 ARIA tree 控件。检索日期：2026-10-28。

## 细粒度调节

“更细、标准、更粗”对应可解释的工作段目标，而非只切换一个显示标签。更细默认 25 分钟，可设 5 至 30 分钟；标准默认 45 分钟，可设 25 至 60 分钟；更粗默认 90 分钟，可设 45 至 120 分钟。目标分钟是本次调整的工作段目标，不是对注意力极限的科学断言。

例如，将一个预计 60 分钟的未开始清单以 20 分钟细化，得到三个同级工作段，合计仍为 60 分钟。它们仍处于第四层，保留原任务来源；已经完成或正在进行的清单不拆。更粗只组合兼容的同父相邻清单，不能跨阶段吞并已有成果，也不能跨过受保护节点。

细化时目标分钟作为上限，剩余时间均匀分配，避免留下很短的尾段。合并只接受日期、截止要求和状态相容的邻项；一个已大于合并目标的原任务不会因为选择“更粗”而反向拆分。

用户先选择范围和目标分钟，点击预览，再核对任务数量、总时长、保留数量及逐项变化。没有实际变化时，不重复生成一份同样的正式计划。重复细化不会无限给已经足够短的工作增加层级。

这里的时间分段采用确定性规则，不调用模型猜测新的交付物。名称中的分段表示同一工作在不同时间继续执行，不能冒充语义上不同的子目标。需要改变任务内容时，使用规划草案编辑或修改规划流程；模型产生的内容同样需要用户审阅。

任务粒度与作息周期是两层控制：把任务合并成 60 分钟，不代表必须连续工作 60 分钟；若作息规定每 20 分钟休息，日历仍会将它安排为多个工作块。日历切块不会额外增加任务树层级。

## 作息调整

作息同时约束“什么时候可以工作”和“连续工作多久要休息”。工作开始必须早于结束；午晚餐从可用区间扣除。专注分钟、短休息分钟、恢复分钟及恢复周期共同形成工作节拍。休息具有独立类型，不会成为需要勾选完成的任务，也不会被传给 Focus 当作待执行任务。

以 09:00 至 12:00 的工作窗口、25 分钟专注、5 分钟短休息为例，前几个工作段之间应留出真实的五分钟空档；若每四轮采用较长恢复，则该轮使用恢复时长。休息会占用时间，所以扣除用餐后的可用时段并不等于净工作产能。预览必须显示这一影响，而不是继续塞入原来那么多工作。

调整前后对照包括工作窗口、节拍、受影响任务、工作分钟、休息分钟和截止风险。可指定生效日期：此前沿用原作息，此后只重排尚未执行的工作，正在进行和已结束的记录保留。保存失败、草案过期或别的窗口已经改动计划时，应重新读取再预览；不能静默覆盖。

主 APP 的面板集中设置工作窗口和专注休息周期，并显示当前用餐安排；独立 Scheduler 的完整作息表单可编辑午晚餐时段。摘要中的工作和休息分钟是预排范围的总量，每日可用分钟则是工作窗口扣除用餐后的长度，二者不能混用。

休息段用于预留日程，不会自动暂停正在运行的 Focus 会话，也不会改变其提醒设置。本轮没有修改 Focus 的计时行为。工作窗口暂不支持跨午夜。

独立窗口的时段外操作提示仅根据用户实际处理任务的时间作建议：至少两次落在工作时段外才提示检查作息，采纳仍走预览和确认。这是操作时间的简单启发式，不是睡眠检测、疲劳诊断，也不是自动学会了用户的生物节律。

## SYA UI 使用流程与接口

从主 APP 的规划入口输入目标，生成草案并检查四层任务。确认后切换日、周、月或项目筛选，选择清单开始专注。任务变得难以启动时进入粒度调整；可用时间改变时进入作息调整。两种调整都先预览，随后确认或取消。

正式调用路径是 Scheduler 页面 → feature API → preload IPC → FunctionHost → Scheduler HTTP 服务。渲染层不掌握服务端口、文件路径或模型密钥。独立窗口只使用同源 HTTP 和 WebSocket。

- `plans.preview`、`plans.commit`、`plans.cancel`：生成、确认及取消草案；确认携带 `expectedRevision` 与幂等 `requestId`。
- `granularity.preview`：接收 `projectId`、`taskId`、`level`、`targetMinutes`，保留外部传入的原因和真实会话关联。
- `routine.preview`：接收工作窗口、目标日期、时区和工作休息周期，返回变更摘要与预排时段。
- `tasks.tree`、`tasks.list`、`timeline.get`：回读所属项目、节点、进度和统一日程；日历的工作事件与休息段分别展示。
- `schedule.granularity_applied`、`schedule.routine_applied` 等事件用于记录已采纳的调整；取消和单个检查点不能算作一次完整规划对话。

Scheduler 不创建第二套 Focus session ID。其他模块已有的事件只作为上下文，用户没有确认时不改计划。本轮没有扩展其他模块的功能。

## 如何判断持续专注

应回答“这段时间有哪些支持持续在任务上的证据”，而不是只给一个看似精确的专注分数。计时、行为、任务成果和用户自评反映不同方面，需要对齐同一 `taskId`、`sessionId` 和时间区间。没有数据的时间必须保留为未知。

**当前已实现的证据**：Scheduler 保存任务状态、预计时长、可选实际时长及计划调整事件。主 APP 现有 Focus 接口提供会话状态、活动计时、检查点和分心事件计数；Monitor 的记录类型包含状态、时间、来源、置信度及暂停或断连边界。这些是现有对接字段，Scheduler 本轮没有新增跨模块自动评分器。

任务标记完成只能说明用户声明交付完成。计时器运行只能说明会话处于活动状态。没有记录分心不等于没有分心；低置信度、断连、暂停和离开设备也不能补成专注。看着任务窗口不证明在思考任务，离开键盘也可能是在纸上推导。

Scheduler 旧进度检查中的完成率已修正为只统计 `DONE`，跳过不算完成。兼容字段 `procrastination_index` 只是有实际时长的已完成任务的平均超时比例，不能解释成拖延人格或注意力分数。没有执行样本时不提出细化或合并建议；新确认流程仍需用户明确采纳。

**建议的后续评估方法，尚未实现**：将会话按真实事件时间分段，排除主动暂停和计划休息；每段记录“在任务上、偏离、离开、未知”。只在来源有效、时间覆盖可靠时计算指标，同时保留样本数和来源版本。低负担的自评可在工作段结束或经用户同意的稀疏采样点询问“刚才主要在做本任务、想本任务、处理其他事，还是不确定”。措辞和采样频率会影响结果，应预先固定并报告。[2][3]

建议分别报告四个量：有效观测时长占活动时长的比例；在任务上时长占有效观测时长的比例；无中断且无观测缺口的最长在任务上区段；经用户确认的偏离次数与回到任务所用时间。最长区段不能跨越未知区间拼接，计划休息也不应被计为分心。

**示例，非实测结果**：一段 30 分钟活动时间中，仅 24 分钟有有效观测，其中 18 分钟在任务上。覆盖率为 80%，在已观测时间中的在任务比例为 75%，另有 6 分钟未知。即使两项比例较高，也不能推出“连续专注了 30 分钟”；还需知道那 18 分钟是否被中断。样本不足时应呈现“证据不足”，而不是补一个高分。

真正检验改进效果，需要以同一人的相近任务作比较，同时看成果质量、完成时间、连续区段、主观负担和误提醒率。可先比较固定粒度与可调粒度，再比较无休息约束与明确休息节拍，控制任务难度和时段。以上是后续研究方案，不是已经完成的实验或疗效结论。

## 创新点与参考来源

本模块的创新定位是面向 SYA 场景的工程组合，尚无证据支持“算法首创”或“已证明提升专注力”。四层目标结构、分钟级工作段、来源关系和日历安排连在一起，让用户在细化后仍看得到主线目标。执行保护、变更预览、版本校验和幂等确认使调整可解释且可恢复。主界面与独立窗口共用服务端排期，避免各算一份时间表。

对专注的支持来自降低下一步启动成本、安排恢复时间以及提供可核查的执行证据。是否改善持续专注，必须通过上节的评估方案验证，不能从“功能已实现”直接推导。

**A5 参考说明**：参考其“持续保存上下文、根据变化提出建议、用户确认后执行”的产品思路。[1] Scheduler 将这些思路限定在计划偏好、任务来源和调整草案中。本文未复用 A5 代码、模型或安装包；截至检索时，作者仍写明源码即将公开。其长期记忆和后台主动发现机制不属于本轮实现，也不作为专注有效性的证据。

采用本项目已有 FastAPI、Pydantic、React 和原生浏览器能力，没有引入新的代理框架、外部日历服务或优化器。当前规则可由有界拆分、相邻合并和确定性排期表达；复杂求解器只会增加维护成本，暂不需要。

## 演示与验收

建议用合成目标“完成研究汇报”演示：创建四层草案，修改清单后确认；完成一个清单，选择另一个未开始任务设为 20 分钟细化；取消一次并确认原计划不变，再预览并采纳；切换日周月核对同一批工作段；设置工作窗口与 25 分钟专注、5 分钟休息，核对真实间隔和截止风险；确认后退出并重开应用，检查任务与作息仍在。

异常演示包括无可调整内容、非法作息、模型失败、取消生成和旧版本草案。正式发布前仍需提交子模块变更、核对父仓库引用并验收实际安装包；本地源码测试不能替代签名、打包或真实模型验收。

本次验证通过：59 项 Python 测试、18 条浏览器流程、15 组独立窗口 Electron 操作，以及主 APP 的 34 条真实 Electron 路径。原生验证包含退出重启、Scheduler 持久化和进程清理；模型边界使用固定示例回复，未验证真实模型供应商、真实注意传感器或发布安装包。详细证据见 `docs/research-timeline-ui/EVIDENCE.md`。

代码整理聚焦确定无用的重复逻辑：服务器保留唯一排期算法；静态页分开 HTML、样式和交互；主 APP 的 Scheduler 页面拆为职责清晰的组件。保留原合同与必要兼容入口，不因精简而删除旧项目数据或改变其他模块。
